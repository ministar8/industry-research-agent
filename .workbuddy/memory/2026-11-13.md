## 摘录截断修复 + 请求级指标

### 摘录（`helpers.numbered_sources`）

- 原实现：`content` 存最多 4000 字，但 `numbered_sources` 只取 `excerpt[:600]`，且不标注截断。
  Analyst 把「前 600 字没有」当成「不存在」，信息缺口判断失真。
- 现实现：`EXCERPT_CHARS = 1500` + `excerpt()`，截断时追加「（节选，全文共 N 字，此处为前 M 字）」。
  **只有真正截断才标注**，否则模型会习惯性不信任完整摘录。
- `MAX_CONTENT_CHARS` 保留 4000：存储成本（每轮约 12KB）不是瓶颈，保留全文便于后续按需深读，
  且标注里的 N 才是真实页长而不是被二次截断的假值。

### 指标（`core/metrics.py`）

- `TurnMetrics` + contextvar；`begin_turn` / `end_turn` 放在 service 的两个入口
  （`invoke`、`message_generator`），节点只调 `record_*`。
- 一行日志：`turn thread=.. status=ok elapsed=29.4s llm_calls=8 tokens_in=26196 tokens_out=3866
  reasoning=0 search=4 fetch=2 search_failed=0 fetch_failed=1 degraded=-`
- 不写进 `ResearchState`：描述单次请求，不该进入 checkpoint。

### 真跑暴露的三个问题（均已修）

1. **token 全为 0**：模型 `streaming=True` 且未开 `stream_usage`，流式响应不带 usage；
   而 `with_structured_output` 返回 pydantic 后 `usage_metadata` 已丢失。
   修法：`include_raw=True` 保留 AIMessage 再读 usage。
2. **json_mode 被数组包裹**：DashScope 返回 `[{...}]`，重试后升级为 `[[{...}]]`。
   修法：`_JsonPrompted._repair` 递归解开单元素数组后再用 schema 校验，真正不匹配仍抛错。
3. **流式 + json_object 返回 token id**：实测出现过 `[2026, 2025, 4, 5, 5, 1, ...]` 这类输出。
   修法：两个 provider 全部 `streaming=False`。本图没有 token 级流式需求（finalize 整段返回）。

### 评估集发现的三个真问题（均已修）

1. **`[[6,7,8,9,10]]` 在 streaming=False 下仍复现** → 此前归因错误，流式不是原因。
   实测百炼支持 `response_format: json_schema`（200 且输出正确），改为优先 json_schema 约束解码，
   JSON mode 作为回退，能力按模型 id 缓存（`_STRICT_SUPPORTED`）。catl 用例 0/7 → 7/7。
2. **输出撞 8192 上限整轮失败**（`LengthFinishReasonError`）：ess-cell 与 reducer 各一次。
   修法：`LLM_MAX_TOKENS` 8192 → 16384（实测 32768 也被接受）；捕获长度异常后用
   `_LENGTH_RETRY` 压缩提示重试一次，并把失败那次已消耗的 token 计入指标。
3. **失败调用的 token 未被统计** → `_record_failed_usage` 从异常的 completion.usage 补记。

### 验证被余额中断

- 19:26 起 DeepSeek Search 返回 **402 Insufficient Balance**，检索全部失败。
- 由此暴露一个真缺陷：`_post` 对非重试 4xx 直接 `return {}`，被计为「成功检索」，
  于是空转 5 轮、20 次调用、每轮都白跑，用户只看到「未采集到可用信息」。
- 修法：新增 `SearchRejected` 异常（非重试 4xx 抛出）；researcher 在「全部查询被拒」时

  「检索服务拒绝了本次请求…余额不足或 Key 失效」。
- 实测效果：17s/11 次调用/20 次检索 → **5.2s/3 次调用/4 次检索**，且原因明确。

## 切换到 deepseek-v4.1-flash-1017 + 成本归因

- 模型：`DashScopeModelName.DEEPSEEK_V41_FLASH_1017`，设为默认（settings 内 DashScope 分支）。
  实测可用（HTTP 200），ess-cell 用例 8/8、44.4s。
- 指标增加按节点归因：`structured_output(..., label=...)` → `record_usage(..., label)`；
  `TurnMetrics.calls` 保存 `label -> {calls,in,out}`，DEBUG 级别输出 `turn breakdown`。
  标签：supervisor / planner / judge / analyst / writer。
- 单轮实测（ess-cell，8 次调用，31,850 in / 5,861 out）：
  writer 12,037in / analyst 9,842in / judge 6,099in / supervisor 4×3,511in / planner 361in。
  → writer+analyst 占输入 69%，judge 占 19%。
- 成本高的主因：同一批 12 条来源（摘录 1500 字）**被 analyst 和 writer 各付一次**；
  加上 judge 送 16 条候选摘要，以及无有效前缀缓存（各节点 system prompt 不同）。
- `PRICE_PER_MTOK` 暂无 1017 的快照价，评估表成本列显示 "—"，不臆造价格。

## Writer 去摘录的实测（回答「质量会不会受影响」）

同一批来源、同一份分析，只切换 writer 的输入视图，跑了两轮（`evals/ab_writer.py`）：

| 变体 | 输入 | 输出 | 字数 | 未溯源数字 | 表格行 |
|---|---|---|---|---|---|
| 带 12 条摘录 | 13,381 | 1,016 | 1,607 | 0 | 27 |
| 仅编号索引 | 5,046 | 2,175 | 3,376 | 0 | 21 |

第二轮（不同来源集）：带摘录 12,550in / 2,089 字；索引 3,426in / 3,562 字。
→ 两次都是「去摘录」更省且写得更长；带摘录那次有一份报告分析段被截断
  （`## 分析` 只有「出货格局呈」，紧接 `## 结论`）。

结论：writer 的职责是成文，原文摘录是噪声源。已改为默认不传摘录，
分析 < 1500 字时自动回退（`MIN_ANALYSIS_CHARS_FOR_INDEX`）。

## 代码审查与修复（3 必修 + 4 建议）

必修：
1. `supervisor()` 在 `abort_reason` 已置位时直接返回 finalize，不再多打一次模型（此前余额不足那轮 llm_calls=3，含一次空转）。

3. `_render_table` 新增 `_cell()`：转义 `|` 与换行，避免单元格破坏列数。

建议：
4. `finally` 里 `if outcome != "closed"` 才发 `[DONE]`，规避 GeneratorExit 下 yield 的 RuntimeError。
5. `numbered_sources` 不传摘录时**整行省略**「摘录:」，省约 120 token/轮（原来打印「（略…）」占位）。
6. `excerpt()` 只在需要时才计算。
7. `_STRICT_SUPPORTED` 的键改为 `model_name@base_url`，避免同模型不同端点误用缓存。
