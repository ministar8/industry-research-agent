## 追加：检索层迁移到 DeepSeek Search / Fetch（已用真实 key 跑通）

官方接口（2026-10-17 上线）：`POST /v1/tools/search`、`POST /v1/tools/fetch`，¥5/1000 次成功请求，仅 HTTP 200 且返回非空时计费，失败可免费重试。

实现：
- `search.py` 重写：`search()` / `fetch()`，429/5xx 退避重试 3 次，4xx 不重试；query 截断 128 字符，count 限 1-50；`ori_question` 传 intent。
- `Source` 增加 summary / content / site_name / published_at / authority / rerank_score。confidence 由 `confidence_from_authority()` 从 authority+rerank 归一化，LLM 不再打分。
- `_judge` 降级为只判相关性；`_deep_read()` 只对 authority≥3 或 rerank≥1.5 的前 3 条 Fetch，正文截 4000 字。
- `url_key()` 按语言段（/cn/ /tw/）归一化去重 —— Search 会同时返回简繁体同一篇，否则一篇被当成两个独立来源参与交叉验证。

**三个只有真跑才能发现的 API 限制**（写入 CLAUDE.md）：
1. `response_format: json_schema` → 400 "This response_format type is unavailable now"
2. `tool_choice` 强制 → 400 "Thinking mode does not support this tool_choice"
3. `json_object` → 200，但 prompt 里必须出现 "json" 字样，且不会注入 schema；模型会自己编字段名（`next_agent` 而非 `next`）
   → 解法：`structured_output()` 统一走 json_mode + `convert_to_openai_tool(schema)` 把 schema 序列化进 prompt + 解析失败重试一次。

**thinking 模式吃满预算**：`reasoning_tokens=65536` 且 `text_tokens=None`，报错表现为 "Could not parse response content as the length limit was reached"。修法：DeepSeek 模型强制 `max_tokens=8192`；同时 MAX_ROUNDS 8→5、analyst/writer 只看前 12 条来源、prompt 加"直接输出不要推演"。耗时从 4m56s 降到 1m56s。

实测结果（2025 储能电芯问题）：4 Search + 3 Fetch = ¥0.035，输出 4220 字报告，表格、时间/地区约束、排除上游全部生效，引用锚点 [1]-[11] 与附录完整对应。

未解决：`prompt_cache_hit_tokens=0` —— SUPERVISOR_PROMPT 与每轮变化的 status_block 拼在同一个 system message 里，前缀必然变化，缓存永不命中。要修需把可变状态移到消息尾部。

## 追加：Qwen3.8-27B vs DeepSeek 实测结论（重要，推翻了先前假设）

两层 A/B（`scripts/ab_bench.py` 可复跑）：

**第一层 全链路**（同一问题，各自检索）：
| | DeepSeek | Qwen 无思考 |
|---|---|---|
| 耗时 | 107.1s | 88.0s |
| LLM 调用 | 8 | 8 |
| 输入 token | 23,221 | 24,937 |
| 输出 token | 18,320（其中推理 13,908） | 3,644（推理 0） |
| 报告字数 | 3,447 | 2,707 |
| 成本 | ≈¥0.104 | ≈¥0.121 |

**第二层 固定同一批 10 条来源，只换 LLM**：
- DeepSeek：analysis 2,155 字 / report 2,412 字 / 表格 14 行
- Qwen：analysis 1,291 字 / report 1,022 字 / **表格 0 行**

**结论**：
1. 质量差距明显。DeepSeek 的报告有 5 条具体矛盾（含「楚能列第一但报价 0.295 高于天合 0.290」）、8 处「单源未验证」标注、主动把含 2026 年数据的来源排除在事实基线外。Qwen 只有 2 条浅层矛盾、无单源标注、**完全没遵守「用表格」的约束**。
2. **成本假设被推翻**：Qwen 关思考后输出少 5 倍，但输入单价是 DeepSeek 的 2.8 倍且输入占比大，最终 ¥0.121 > ¥0.104。之前"关思考更省钱"的推断错误。
3. DeepSeek 的 13,908 推理 token 买到了实质分析深度，不是浪费。
4. Qwen 唯一优势是速度（34s vs 93s）。

建议：LLM 保留 DeepSeek；若确实要省，只把 Qwen 用于 query 生成和相关性判定（这两步对推理无依赖），Analyst/Writer 留给 DeepSeek。或 Qwen 开 thinking + budget=4096 再测一次。

清理：临时 json 与 `scripts/ab_llm_only.py` 已删，保留 `scripts/ab_bench.py` 供复跑。

## 追加：百炼托管的 deepseek-v4.1-flash 实测

百炼（DashScope）上有 `deepseek-v4.1-flash`，用同一把 DASHSCOPE_API_KEY。关键差异：**百炼能用 enable_thinking 控制思考，DeepSeek 官方不能**。

实测参数行为：
- `enable_thinking=false` → reasoning=None，输出干净 ✅
- `enable_thinking=true + reasoning_effort=low` → 短 prompt 下 reasoning=20 ✅
- `enable_thinking=true + thinking_budget=1024` → 短 prompt 下 reasoning=13 ✅
- **但长 prompt 下 thinking_budget=4096 不生效**：max_tokens 提到 16384 仍报 `LengthFinishReasonError`。结论：百炼版思考一开就不可控，实际只能用关闭模式。

关闭思考后的表现（analyst+writer，同源）：
- 17.8–23.4s（官方思考版 93s）
- analysis 1968–3330 字，有具体出货量/排名/价格/口径区分
- **但报告 0 行表格、0 处「单源未验证」标注**

代码调整（已落地）：
- `QwenModelName` → `DashScopeModelName`，含 `DEEPSEEK_V41_FLASH` 与 `QWEN_38_27B`
- `Provider.QWEN` → `Provider.DASHSCOPE`
- 新增 `LLM_MAX_TOKENS`（默认 8192），替代硬编码
- `WRITER_PROMPT` 增加硬性表格语法要求（`|` 分隔、`| --- |` 表头），但单次验证发现关闭思考时仍可能不生成表格 —— 说明交付格式遵守依赖推理能力，不能只靠 prompt
- **默认模型回退为官方 `deepseek-flash`**：只有它稳定产出带表格和证据分级的报告

遗留可选改进：把 `ReportBundle` 增加 `tables: list[TableBlock]` 字段，由代码渲染 Markdown 表格，这样表格不再依赖模型自觉。

**用户决策（2026-11-12 20:05）**：用户认为百炼的 deepseek-v4.1-flash 效果更好，要求以此为默认；「表格由代码保证」暂不实现。
→ 已把 `api_keys` 顺序改回 `Provider.DASHSCOPE` 优先，运行时默认 `deepseek-v4.1-flash` + `DASHSCOPE_ENABLE_THINKING=False`。
→ 我的对比结论存在方法论缺陷（每次重新检索导致来源集不同、有一次误传空 sources），归因力不足，已在 CLAUDE.md 中把「表格/单源标注缺失」改写为"需要在自己语料上复核的已知取舍"，而非定论。

用户认为 sqlite 太 demo，选「本机 PostgreSQL」。已用项目自带 `compose.yaml` 起容器（`agent_service` 库，卷 `agent-service-toolkit-main_postgres_data`），`.env` 写入 `DATABASE_TYPE=postgres` + `POSTGRES_*`（localhost:5432/postgres/postgres/agent_service）。

**踩到一个 Windows 专属坑（重要）**：
- 现象：启动 30 秒后 `PoolTimeout: couldn't get a connection`，日志提示 `Psycopg cannot use the 'ProactorEventLoop'`。
- 根因：`uvicorn >= 0.54` 的 `asyncio_loop_factory` 在 Windows 上**硬编码返回 `asyncio.ProactorEventLoop`**，完全绕过 `asyncio.set_event_loop_policy`。所以 `run_service.py` 里原有的 `WindowsSelectorEventLoopPolicy` 那行一直是死代码。
- 修法：`run_service.py` 在「Windows + DATABASE_TYPE=postgres」时改为手动构造 `uvicorn.Config` + `uvicorn.Server`，用 `asyncio.run(server.serve(), loop_factory=asyncio.SelectorEventLoop)`。这条路径失去热重载，已在启动时打印 warning。
- 已写入 CLAUDE.md，防止后人「简化」回 `uvicorn.run`。

其他：MongoDB 的 store 仍不支持（`initialize_store` 只有 postgres/sqlite 分支）；tests 不受影响，204 passed。
